## Purpose

Use a retrospective after a milestone, sprint or project completion to learn **which decisions worked, what actually went wrong, why, and what will change next**. This is a constructive team review; do not use it to assign blame or invent success metrics.

## Suggested 30-minute session

| Time | Activity | Output |
| --- | --- | --- |
| 0–5 min | Confirm objective, scope, timeline and the actual work completed | Shared factual context |
| 5–12 min | Identify two outcomes that created value, citing work evidence | Strengths to repeat |
| 12–20 min | Examine one or two blockers/quality incidents and causes | Lessons based on evidence |
| 20–27 min | Agree no more than three actionable improvements | Owner, task and date |
| 27–30 min | Confirm risks still open, sign-off and where learnings will be stored | Next actions agreed |

## Fictional example (do not copy as real delivery)

**Issue:** A dashboard release was delayed because column definitions differed between two data sources. **Cause:** The team had not agreed source-to-target contracts before building visuals. **Action:** Add a schema-contract review before dashboard development; assign a data owner and check one approved sample in the next project. **Evidence:** Signed review record and a successful automated schema test.

## Review before saving

- [ ] Statements reflect actual delivery and credible evidence.
- [ ] Consequences are realistic; no unsupported percentages or blame.
- [ ] Improvement actions are specific, assigned and time-bound.
- [ ] Confidential/client/personal information is removed for public summaries.
- [ ] Share the approved outcomes with the team and update relevant issues.
