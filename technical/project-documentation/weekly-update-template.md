## Why use a weekly update?

A weekly update should help team members understand **what was actually delivered, what remains, why progress might be at risk and who needs to act**. It should not ask volunteers to write long reports or retype information already visible in GitHub. One useful update can be completed in around five minutes when the issue board is current.

## How to complete it

1. Copy this template into the approved project workspace; do not fill out the shared blank template.
2. Link to actual merged pull requests, demos, tests or documents; **activity alone is not completion**.
3. Report status as **Green** (on track), **Amber** (delivery risk needs attention), or **Red** (blocked / critical decision needed). Use the real agreed milestones, not arbitrary optimism.
4. State blockers neutrally and request a specific decision or assistance with a named owner/date.
5. The Project Lead summarises, validates and shares one concise team update.

## Example: concise factual update (fictional)

**Status: Amber.** The source-import test suite is complete and 12 validation checks are passing. The dashboard release is not approved because the sample schema changed and the updated contract needs review. The data lead will confirm the schema by Thursday; the team will then rerun regression checks. Next week the priority is an approved demo using permission-cleared sample data.

This says **what is finished, what remains, the dependency and owner**; “80% complete” without an agreed denominator would be less useful.

### Quality gate

- [ ] Dates, repository and issue IDs are correct.
- [ ] Progress describes actual outcomes and evidence, not activity counts.
- [ ] Status matches real risk and upcoming milestone.
- [ ] Each unresolved blocker has a clear owner, next action and due date.
- [ ] No protected credentials, participant/client or private contributor information in public channels.
- [ ] Contributors and leader know what is expected next.
